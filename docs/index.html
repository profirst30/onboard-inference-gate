Onboard inference gate

A partner model only goes to orbit if it fits the target's budget, and the spacecraft refuses a file that does not match what was compiled for it.

The problem, as I understand it

From the ML Runtime Engineer posting and the On-Orbit AI page: partners hand over ONNX models, and each one must be turned into an engine for a given onboard accelerator, inside power and thermal budgets. The ground side has to prove a model fits before upload, and the onboard side has to reject an engine built for another target.

This is a small, CPU-only version of that path, built in a day to show how I would approach it.

What it does

  1. 1 · Partner modelA small CNN trained on EuroSAT (Sentinel-2 RGB, 10 land-cover classes), exported to ONNX.
  2. 2 · INT8Static post-training quantization (QDQ, per-channel), calibrated on training images.
  3. 3 · SensitivityQuantize every layer but one, measure accuracy, find the costly layer, then fix the cause.
  4. 4 · BenchLatency p50/p95/p99, session memory, size, accuracy, and which execution provider runs each node.
  5. 5 · GateBudgets per target in YAML; a model is accepted only if it passes every check.
  6. 6 · ManifestSHA-256, target, opset and input shape; the target refuses any mismatch before loading.

Which layer costs the accuracy?

Each row quantizes every Conv/Gemm to INT8 except the one named, then measures accuracy on the held-out images.

What the numbers say

  • Full INT8 cuts the file to under a third of the FP32 size, but the default U8S8 model fails the accuracy budget, whatever the calibration method.
  • The sensitivity run points at one layer, the first convolution. Keeping it in FP32 (mixed) restores accuracy, but only hides the cause.
  • The cause is the CPU kernel, not the model. Input quantization is lossless (pixels are already k/255) and the first layer's weights have the smallest quantization error in the network. This Zen 3 CPU has AVX2 but no VNNI: U8S8 kernels add pairs of u8×s8 products into 16-bit integers, which can saturate, most of all in the first layer, fed with raw pixels over the full 0–255 range. 7-bit weights (reduce_range, model _rr) keep the sums in range: full INT8 at FP32 accuracy.
  • The same INT8 file loses accuracy or not depending on the hardware that runs it: the strongest argument for validating every model on every target.
  • On this CPU, INT8 is still not faster than FP32 for a model this small: quantize/dequantize steps and layout changes cost more than integer arithmetic saves. INT8 buys size here, not speed.

Limits

  • Measured on a laptop CPU only. I have no Jetson, Hailo or AMD hardware: TensorRT and the other providers are untested. The bench takes --providers, but those numbers do not exist yet.
  • No power or thermal measurement, which is the real constraint onboard.
  • Latency on a laptop is noisy (power management, background load): p99 moves between runs.
  • Session memory is the rise in the process's peak working set; it is an approximation.
  • The model is deliberately small (64×64 images); real partner models are far larger.
